# V18-01A / E-FIX-02 — Outbox identity namespace race

Date: 2026-11-03. Scope: **P1-03 only**. Branch: `v18-01a-outbox-recovery`.
Base: `46fe242928dab376b96998cea8c60b6b27b3f4a9`; branch, HEAD and clean Git status verified before editing.
Overall V18 release decision remains **HOLD**. Stop before E-FIX-03; no deployment or merge.

## AUDIT → RISK → MINIMUM FIX

Reviewed `v18-01a-phase-e.md`, `v18-01a-e-fix-01.md`, the reproduction README and unchanged R5, plus Outbox, identity owner/partition, gameplay-write and Dead-Letter.

Outbox previously resolved its logical fallback key through the active identity *after* awaiting Web Locks or IndexedDB. An Alice operation could therefore write into Bob's physical fallback namespace. Filtering by `userId` hid the operation from Bob but did not return it to Alice. Reads, recovery cleanup and conditional mutations had the same missing lifetime fence. The gameplay adapter checked identity only after persistence, too late to protect storage.

Risk: stopping only at gameplay callers leaves direct Outbox callers unsafe. Retargeting logical keys during recovery can also clean another owner's fallback after the primary copy commits. Rolling back a completed write would lose valid progress. A storage migration, clearing data, schema change or identity-partition redesign is neither needed nor used.

Minimum fix: capture one operation scope before waiting, reuse its explicit physical fallback key, reject stale owner/epoch work and abort only transactions that have not committed. Keep already committed snapshots. Preserve revision comparisons, V17 serialization and the archive-before-conditional-remove contract.

## IMPLEMENT — owner protection

`src/lib/offline/outbox.ts` now captures the Storage object, active owner, identity epoch, requested user and physical fallback key at API entry, before lock acquisition or payload serialization. It recognizes the actual installed partition using the existing read-only `__originalGetItem` marker, as E-FIX-01 does. It does not patch Storage or change the partition.

- `enqueue` delegates synchronously to fenced `enqueueWithId`; `peekAll`, `remove` and `bumpAttempt` capture their scopes at entry. Explicit foreign-user or guest-owner requests fail closed in partitioned runtimes.
- Coordination checks the scope after obtaining the lock and after the asynchronous operation, before returning its result. An Alice → Bob → Alice round trip is rejected by the epoch even when the final owner matches.
- IDB operations check before/after opening and inside the request callback before applying changes. An owner-change subscription aborts an uncommitted transaction and is removed on completion/error/abort. Completion checks again before exposing a result.
- A transaction that already committed is never compensated by deletion. A changed identity causes rejection rather than a stale success receipt or a second fallback write; the committed data remains available to its owner.
- Fallback reads check before and after access. Writes and recovery cleanup check before and after access and always use the captured physical key. No operation follows a new active namespace.
- `readBoth` checks identity after both reads settle, before returning complete or partial account data. `recover` uses the same scope for IDB copy, commit and exact-snapshot fallback cleanup. A switch after copy retains the backup as well as the primary copy until a subsequent valid recovery.
- Recovery copies/cleans only the scoped user's fallback rows in partitioned runtimes. A foreign historical snapshot already inside that array is preserved in place, without guessing a new owner namespace or migrating user data.

The database remains `irth-offline-outbox`, version 1, store `items`, key `id`; fallback name and Web Lock name are unchanged. Same-id account collisions still remain durably in the appropriate fallback. V17 rows without revisions continue to use canonical snapshot comparisons. Revision, supersedes/recoveryBase ancestry, stale acknowledgement rejection and conditional deletion are preserved. Unpartitioned legacy runtimes retain the original shared-key behavior; the application installs the real partition at startup.

No changes to `owner.ts`, `partition.ts`, `gameplay-write.ts` or `dead-letter.ts` were necessary. The existing independent-realm recovery harness only gained loaders for Outbox's identity imports; no existing assertions were changed or relaxed.

## TEST — acceptance and regression

New file: `tests/offline/outbox-identity-partition.test.ts`: **29 acceptance tests** using real `installIdentityPartition`, jsdom localStorage, fake IndexedDB, a fake Web Lock service and a mocked auth/RPC server. External `fetch` is forbidden.

Coverage includes:

- Both enqueue APIs blocked on a lock during an account switch and IDB outage; owner/epoch mismatch including Alice → Bob → Alice.
- Switching during asynchronous IDB open, fallback read/update, recovery read and cleanup, and after a recovery copy has committed.
- Switching after `put` succeeds but before transaction commit (abort), and after an enqueue or fallback write commits (retain data, reject stale success).
- `peekAll`, `remove` and `bumpAttempt` across lock waits; mutations during their conditional IDB read; all four explicit foreign-owner entry points.
- Both accounts retaining operations together, colliding V17 ids, restart/module reload with persistent storage, Alice returning, Bob never receiving Alice's rows, and no cross-account dequeue.
- Missing Web Locks, IDB failure together with switching, no leaked partial reads, preserved foreign legacy snapshots, V17 revisionless rows, and newer revisions surviving old remove/bump calls.
- E-FIX-01 archival for both users and V17 rows, plus a confirmed archive retained when an account switch interrupts conditional dequeue.
- Gameplay does not report accepted/queued success or call the mocked RPC when enqueue is fenced.

## CLOSE — boundaries and remaining risks

No blocker remains in the tested P1-03 scope. The code/tests and this report are intended for one commit on the authorized V18 branch.

**P1-02 remains unresolved.** This change neither cancels timeout work generically nor adds base-revision CAS for late enqueue ordering. It does not claim to prevent a delayed same-identity enqueue from superseding a newer intent. The existing conditional acknowledgement/delete protection remains; no revision ordering was weakened.

P1-04 through P1-07, previously recorded Startup/hydration issues and Android/WebView/device acceptance remain outside scope. Tests simulate restart by closing IDB handles and reloading modules while keeping storage; they do not prove physical-device force-stop behavior. Fallback mutation still requires Web Locks. An unreadable store still fails closed; historical foreign data already stranded in another physical namespace is not automatically reassigned. A committed write may correctly remain queued even though its old caller receives an identity error, and is recovered when that owner returns.

No application gameplay/rewards, SQL/RPC definitions, Cloud Save, Production/Supabase service, Android preparation, deployment, merge or main-branch change was used. Network access is only needed to push the authorized commit to GitHub. V18 stays **HOLD**.
