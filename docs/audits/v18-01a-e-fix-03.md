## AUDIT → RISK → MINIMUM FIX

Reviewed the Phase E audit, E-FIX-02 report, reproduction README, unchanged historical R4, Outbox/gameplay-write and the existing acceptance suites.

Root cause: enqueue observed a snapshot during recovery, but then built its new payload from whichever row existed in the subsequent write transaction. A paused old enqueue could borrow the newer row's revision as `supersedes`, making an older intent appear to descend from and overwrite newer progress. `saveDeadline` only raced a timer against persistence. The UI deadline released single-flight while the raw write remained alive, and a failed stale save could still reach the generic live-RPC path.

Risk: protecting dequeue alone does not protect payload replacement. UUIDs/timestamps cannot order independent user intents. Treating timeout as cancellation could lie about committed progress, while compensating deletion would lose valid data. Retrying an unresolved write independently could recreate the same race. The minimum fix is snapshot CAS, cooperative cancellation checked at actual persistence boundaries, and a separate raw-write lifetime fence. This needs no schema/storage migration, reward contract change or identity redesign.

## IMPLEMENT

### Snapshot comparison and fallback

`outbox.ts` now preserves the exact base snapshot observed by recovery. Inside the IDB readwrite transaction it compares the current row against that base *before* putting anything. Both absent rows match for a first insert; a changed/appeared/disappeared row rejects with `outbox-stale-enqueue`. The comparison uses full canonical snapshots, including V17 rows without `revision`; it does not infer ordering from UUIDs or clocks. The new receipt inherits only the base actually observed, never an intervening revision.

The fallback path captures its original row under the existing Web Lock and compares it again after asynchronous IDB failure. It cannot silently adopt a replacement fallback row. If recovery already copied/cleaned that exact backup, its absence is permitted; a changed remaining backup is not. Existing ancestry-conflict checks still preserve the durable primary and fallback rather than selecting an unknown winner. No fallback mutation is allowed without a Web Lock.

### Timeout, cancellation and RPC

`enqueueWithId` accepts an optional `AbortSignal`. Its existing E-FIX-02 scope checks cancellation at the same boundaries as owner/epoch, including lock acquisition, IDB open/read/write/completion and fallback access/cleanup. A signal listener aborts only pending IDB transactions and is removed on completion/error/abort. A completed commit is retained. Cancellation is not a storage rollback.

`saveGameplay` creates the signal and aborts it when its existing **8000 ms** persistence deadline expires. `SaveOutcome` has an additive optional `storageState: "unresolved"`; deadline results use `reason: "storage_pending"`, `acknowledged: false`, `queued: false`. This truthfully describes missing confirmation, including a commit whose completion callback has not yet arrived. `saveAccepted` rejects that outcome. The late continuation cannot issue RPC or rewards after that return.

A separate `pendingWrites` map tracks the raw enqueue promise by epoch/user/id until it actually settles. The UI outcome may return earlier, but another payload or retry for that same operation returns bounded `storage_pending` while raw work remains unresolved. Identical currently inflight requests still share the existing promise. Once the raw operation settles, a legitimate retry can proceed. Each independent context also has IDB CAS protection; correctness does not depend on sharing that map across contexts.

Stale/CAS, cancellation and unknown-ancestry/recovery conflicts stop before the live-RPC path with `storage_conflict`; they never claim queued/acknowledged success. Generic storage failures retain the pre-existing live-ack behavior, outside this stale-write change. RPC-timeout behavior, server idempotency keys, reward contracts and gameplay interfaces are unchanged.

The IDB version/store/key, fallback keys, revision ancestry, E-FIX-02 physical owner/epoch scope and E-FIX-01 archive-before-conditional-remove remain intact. No automatic migration, data clearing or reinitialization was added.
