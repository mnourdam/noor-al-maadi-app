# Browser content runtime acceptance lane (pending execution)

This selected-module fixture is not the whole application UI, login flow or native build. This lane builds actual controller, snapshot generator/validator/storage, local-first store and Supabase SDK/client modules with no target-module mocks. Build environment-file loading is disabled and the client URL/key are explicitly synthetic loopback-only values. A separate loopback HTTP server supplies synthetic public content; the browser has a fresh temporary persistent profile, no real auth session, and no production data. Only generated assets are served, never the profile directory.

The planned checks use native Chromium IndexedDB and real HTTP response streaming: hold an incomplete first encyclopedia page until the controller times out, retry a roughly 15 MB synthetic content refresh, verify complete durable content and subsequent ordinary HTTP without restart, identify the held GET and require its browser `requestfailed` event with `ERR_ABORTED` before retry, release the retired stream, simulate CDP freeze/resume, verify offline local/IDB reads, then close/reopen the browser with the same profile and origin. Page requests outside that exact origin are blocked and fail acceptance; service workers and WebSockets are blocked. This is browser context request isolation, not a claim of whole-machine firewall enforcement.

Local execution is blocked before page creation: installed Chromium 156.0.8078.79 fails `process_singleton_posix.cc:297`, `socket() failed: Operation not permitted`, then SIGABRT. The fresh-profile/about:blank probe establishes an environment restriction, not a stale profile or application defect. No security bypass was attempted. Local bundle build and Python syntax validation pass; actual runtime acceptance must run in CI before reporting PASS.

The dedicated repair-branch workflow installs official Playwright 1.62.0 and its Chromium, uses Node 24/locked npm dependencies, and uploads only sanitized result JSON. No APK packaging, signing, deployment, live backend or credentials are used. CDP lifecycle simulation is not Android background/force-stop/device acceptance. Orderly persistent-profile reopening is not crash or OS force-stop durability. Synthetic HTTP content and anonymous SDK configuration do not establish Supabase JWT/RLS acceptance or full app UI correctness.

The positive lane must observe cancellation of the exact held GET, not merely completion of the server's tail write. A separate temporary-build counterfactual replaces exactly one query-signal-forwarding return with `return query`, preserving controller timeout behavior. It must reach the timeout with the held response still pending and fail to observe transport cancellation; unrelated launch/build errors are not accepted as negative-control success. No production source is edited. The synthetic `/health` check proves ordinary local HTTP works afterward, not that the user's production API or full app connectivity is repaired. Reopening loads the fixture assets online before reading durable content; offline reads are a separate explicit step, not offline navigation-shell acceptance.
