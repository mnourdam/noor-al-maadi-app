هذه حزمة أدلة لقرار **HOLD**، وليست إصلاحًا أو بوابة إطلاق. [التقرير الكامل](../../v18-01a-phase-e.md) يحتفظ بمجموعات P1 السبع، والأدلة والأسطر، وMINIMUM FIX، ونتائج الانحدار، وHydration وقائمة Android.

## الأساس والحدود

- HEAD الذي أُعيدت عليه الحالات: `2c4ae3ea442a772f9a6fa2d0a6fd45828a8eeb4a`.
- أساس المقارنة: `fd573b8b881ab8f0e7f566d6d67ec3a5a60a38bf`.
- استُخدمت dependencies المثبتة في المشروع: Vitest 4.1.10 وfake-indexeddb 6.2.4 وjsdom 30.0.1. لا حزم جديدة ولا تعديلات package/lockfile لهذه الحزمة.

- ملف الإعداد مستقل عن إضافات Vite للتطبيق، ولا يحمّل ملفات البيئة. Supabase/auth وdaily-quest وdiag-trace وهمية، و`fetch` محظور. لا مفاتيح أو إعداد خادم مطلوب.
- التخزين داخل jsdom وfake-indexeddb فقط. `localStorage.clear()` يمس fixture الاختبار فقط، ولا يقرأ تخزين متصفح أو جهاز أو مستخدم حقيقي.
- إعادة تحميل modules تحاكي فقد الذاكرة/سياقًا آخر مع بقاء التخزين؛ ليست قتل عملية Android فعلية. اختبار السباق يؤخر تسليم حدث اكتمال قراءة، ولا يدعي اختبار جدولة نظام تشغيل على جهاز.

## التشغيل المستقل

من جذر checkout، بعد تثبيت dependencies المعتاد من lockfile المشروع، شغّل:

```sh
./node_modules/.bin/vitest run --config docs/audits/repros/v18-01a-phase-e/vitest.config.mjs --reporter=verbose
```

لإعادة حالة واحدة، أضف `-t` ومعرفها؛ مثال:

```sh
./node_modules/.bin/vitest run --config docs/audits/repros/v18-01a-phase-e/vitest.config.mjs --reporter=verbose -t '\[R4\]'
```

استبدل `R4` بأي معرف من R1 إلى R8. R4 تنتظر مهلة الـ8 ثوانٍ الحقيقية ولها test timeout مقداره 15 ثانية؛ المجموعة استغرقت نحو 9 ثوانٍ في بيئة التدقيق. لا تستخدم watch أو إعداد التطبيق لتشغيلها.

**النتيجة المتوقعة على HEAD المدقق: 8 passed.** Assertions تتوقع السلوك المعيب الذي لوحظ، وليست تأكيدًا للسلوك الصحيح. بعد إصلاح مانع قد تفشل حالته هنا؛ احتفظ بالأثر التاريخي وأضف اختبار قبول صحيح في مهمة الإصلاح، ولا تستنتج من ذلك انحدارًا تلقائيًا.

هذه الملفات خارج `tests/offline/outbox-*.test.{ts,tsx}` وخارج قائمة `vitest.outbox.config.ts`، ولا تدخل `npm run test` الافتراضي. لم تتغير مجموعة A/B/C/D.

## إعادة إنتاج كل حالة

### R1 — Dead-Letter مع partition الحقيقي → P1-01

1. ثبّت `installIdentityPartition()` الحقيقي؛ خزّن عملية باسم Alice في IDB.
2. نفّذ `archiveRejected` لها؛ تتأكد الحالة من نجاح إزالة العملية بعد الأرشفة.
3. اقرأ `listDeadLetters('alice')`: يظهر `dead-letter-key-mismatch`.
4. خزّن عملية ثانية وحاول أرشفتها: ترفض، وتبقى العملية الثانية في Outbox.

العيب المتوقع: key مادي يحمل owner suffix يُقارن بمفتاح منطقي؛ بيانات الأرشيف الأولى موجودة ولكن القراءة والأرشفة اللاحقة معطلتان.

### R2 — accepted محلي ثم رفض دائم → P1-04

1. اجعل `navigator.onLine=false`، واحفظ `chapter_progress` بحملة وهمية غير صالحة.
2. تأكد أن `saveAccepted=true` مع `acknowledged=false`.
3. أعد online، واجعل RPC الوهمي يرد `invalid_campaign_id`، ثم شغّل flush.
4. راقب `flushed=0, failed=1` وانتقال العملية إلى الأرشيف.

هذا يعيد إنتاج اختلاف accepted عن server-confirmed. لا ينقر واجهة الفصل أو يمنح مكافأة فعلية؛ أثر الواجهة موثق من ترتيب الكود في التقرير.

### R3 — توقف قبل منحة التحدي → P1-05

1. احفظ `game_complete` مباشرة، دون منح profile أي مكافأة.
2. حمّل مسار `recordCompletion` بذاكرة جديدة مع العملية المعلقة.
3. أعد الإكمال: تكون النتيجة `saved=true, firstTime=false`.

العيب المتوقع: وجود العملية يعامل كدليل صرف مكافأة، مع أن المنحة لم تحدث. المحاكاة لا تقتل عملية حقيقية.

### R4 — timeout ثم كتابة أحدث ثم استئناف الأقدم → P1-02

1. عطّل Web Locks وابدأ بـ`scene:0` في IDB.
2. اعترض تسليم completion لقراءة readonly واحدة، وابدأ حفظ `scene:1` عبر `saveGameplay`.
3. انتظر انتهاء مهلة 8 ثوانٍ: يعيد الغلاف `acknowledged=false, queued=false`، والكتابة القديمة ما زالت معلقة.
4. حمّل نسخة module مستقلة واكتب `scene:9`؛ احتفظ بالـrevision الناجح.
5. استأنف القراءة القديمة؛ تصبح العملية `scene:1`، ويشير `supersedes` إلى revision الخاص بـ`scene:9`.

العيب المتوقع: enqueue القديم يستبدل نية أحدث؛ سلامة remove وحدها لا تمنع ذلك. لا تغيّر مدة المهلة أو Assertions لإسراع الاختبار.

### R5 — تبديل الحساب أثناء انتظار القفل → P1-03

1. ثبّت partition، وعلّق الحصول على قفل enqueue لأليس، وعطّل IDB.
2. بدّل owner والجلسة الوهمية إلى بوب، ثم حرر القفل.
3. تحقق أن fallback المادي لبوب يحتوي عملية `userId=alice`.
4. عد لأليس، وأعد IDB، ثم `peekAll('alice')`: تكون النتيجة فارغة.

العيب المتوقع: العملية مخفية في مساحة أخرى؛ لا يُقصد أن بوب يراها بعد فلتر userId.

### R6 — quota في سجل الضيف → P1-06

1. اجعل `Storage.prototype.setItem` يرمي `QuotaExceededError`.
2. نفّذ `guestMarkCompleted` مرتين للقصة نفسها: كلتاهما `true`.
3. نفّذ `addGuestCompletion` مرتين للتحدي نفسه: كلتاهما `firstTime=true`.

العيب المتوقع: قرار السماح بمكافأة يتكرر رغم عدم إثبات حفظ السجل. Assertions تختبر helpers؛ ربط منح الواجهات موثق بالتقرير.

### R7 — restart بعد handoff ثم تعطل قراءة السيرفر → P1-05

1. أكمل تحديًا؛ تكون `firstTime=true` أول مرة.
2. أزل receipt المطابق لمحاكاة handoff مكتمل، ثم أعد تحميل modules لفقد Set الجلسة.
3. اجعل قراءة `game_progress` الوهمية ترمي `offline`، وأعد الإكمال.
4. تعود `firstTime=true` مرة ثانية.

العيب المتوقع: فشل القراءة يتحول إلى قرار مكافأة جديدة بدل حالة unknown. إزالة receipt هنا تجهيز fixture لمحاكاة handoff، وليست ادعاء نجاح اتصال بخادم.

### R8 — claim دائم قبل profile grant → P1-05

1. نفّذ `claimChapterReward`؛ تكون `granted=true` ويُكتب ledger.
2. لا تستدع `addPoints/addDinars`؛ حاكِ توقفًا قبل المنحة بإعادة تحميل modules.
3. أعد claim لنفس الفصل: تصبح `granted=false`.

العيب المتوقع: لا توجد نية منحة قابلة للاستئناف لتمييز claim غير المصروف عن المنحة المصروفة.

## حدود التغطية والأدلة المحفوظة

- الحالات الثماني لا تعادل سبعة اختبارات لكل مجموعات P1: R3/R7/R8 تغطي P1-05، أما **P1-07 (Daily Quest/account switch)** فدليله تحليل مسار في التقرير؛ لا يوجد له اختبار واجهة ديناميكي ضمن هذه الحزمة.
- P1-04 يغطي التخزين/flush ديناميكيًا؛ منح واجهات اللعب موثق بالأسطر. لا يُدعى أن probes تشغّل واجهة اللعبة كاملة أو تختبر مكافآت backend.
- `evidence/*.log`: نتائج التدقيق الأصلية، بما فيها الإخفاقات وbaseline comparisons؛ ليست نتائج جديدة لهذا Commit. طُبّعت المسافات في نهايات أسطر السجلات والسطور الفارغة عند EOF فقط دون تغيير المخرجات الفنية. ويحتفظ `archived-repros.log` بإعادة تشغيل النسخة المحمولة: 8/8 بتاريخ 2026-10-15. `evidence/probes.log` هو التشغيل الأصلي للحالات الثماني.
- `evidence/hydration-exception.txt`: الاستثناء التقني الأصلي من Chromium، دون سجلات console/DOM أو حالة مستخدم. مصدر الخلل القديم وحدود التحقق موثقان في التقرير؛ ليس اختبار Android.
- `provenance.json`: hashes للمصدر الأصلي وشرح التعديلات اللازمة للأرشفة. تغييرات probes محصورة في import قابل للنقل، وأسماء R1–R8، والتنسيق؛ Assertions الأصلية محفوظة.
- روابط أسطر التطبيق في التقرير مثبتة على SHA التدقيق حتى لا يتغير معناها مع الإصلاحات اللاحقة.
- تمت مراجعة الملفات المنشورة بحثًا عن قيم tokens/keys/passwords والبيانات الشخصية؛ لم تُنسخ `.env` أو ملفات اعتماد أو session أو قيمة سر بيئة. جميع الحسابات في fixtures وهمية. عدم نسخ console/DOM العام لا يحذف استثناء Hydration أو دليلًا على أي مانع.

لا تنفذ هذه الحزمة إصلاحًا، أو SQL، أو migrations، أو Cloud Save، أو نشرًا، أو دمجًا. يبقى قرار **HOLD** وقبول Android معلقًا كما في التقرير.
